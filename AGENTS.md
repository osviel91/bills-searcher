# Agent Instructions

- This is a single Python 3.12 app, not a package workspace. `app.py` serves the FastAPI/MCP API; `worker.py` claims queued jobs, extracts/embeds files, and indexes them. Supporting boundaries are `jobstore.py` (PostgreSQL, with SQLite fallback for local tests), `object_store.py`, `embeddings.py`, and `storage.py` (Elasticsearch).
- Run deterministic tests with `docker compose --env-file .env --env-file .env.migration run --rm --no-deps app python -m unittest discover -s tests -v`. Focus one test file with `-p 'test_jobstore.py'` (replace with the relevant filename). `scripts/smoke_search.py` and `scripts/evaluate_search.py` call a live service; evaluation requires a human-labeled JSON case file. No lint or typecheck command is configured.
- Run real-service integration checks only with `scripts/run_integration.sh` or `scripts/run_shadow_integration.sh`. Each runner uses a unique Compose project, saves logs under `$HOME/Library/Application Support/BillsSearcher/test-runs`, then removes only that project's containers, network, volumes, and local images. `INTEGRATION_TEST_PATTERN` selects a test file; `INTEGRATION_TEST_FILTER` optionally selects unittest names with `-k`. `--keep-on-failure` retains a failed project and prints its cleanup command; after SIGKILL/host shutdown, recover by exact Compose project label and save logs before scoped cleanup. Never use global prune commands.
- Compose uses `.env`, `.env.runtime.app` (from `.env.runtime.example`) and `.env.migration` (from `.env.migration.example`). The migration URL/admin credentials are only for PostgreSQL and the one-shot `schema-migrate` service, never API/worker; `DATABASE_URL` must use the separate runtime role. Keep credentials out of source control. Do not send real invoices to an embedding endpoint until its location and data controls are verified; use synthetic/anonymous documents for remote endpoints.
- Embedding model, provider, document mode, and vector dimensions must agree with the Elasticsearch index mapping. Changing model/dimensions requires a new index and reindexing; the app rejects a dimension mismatch.
- `docker compose --env-file .env --env-file .env.migration down -v` deletes local PostgreSQL, Azurite, and Elasticsearch data. The README is the source for setup, API, and deployment details; `docker-compose.portainer.yml` is for Portainer deployment, not local testing.

## Software Docs governance

- The authoritative Software Docs project is `Búsqueda semántica local de facturas` (`01a11d13-98db-75a9-a819-84e34ef5a758`). SHARED is approved architecture; read its relevant resources before designing or implementing an architectural increment.
- Use one owned MY WORK context per increment and keep only one active by default. Reuse it while work continues; allow parallel contexts only for justified independent work. Do not accumulate contexts for dependent phases.
- Keep MY WORK truthful to implemented and technically validated behavior. Assess affected SHARED resources, relationships, additions, updates, dependencies, and overwrite risks; choose representations by evidence, not by diagram quota. Leave experiments and historical/operational detail private unless it carries durable architectural knowledge.
- At a verifiable checkpoint, run relevant tests, validate MY WORK, compare exact paths, content, and cross-references against current SHARED, then submit only the selected resources as an Architectural Proposal. Check for stale workflow/status prose. Use the promotion preview to verify exact ADD/UPDATE/RETIRE targets; do not infer operations from matching paths or titles. Retire superseded resources explicitly rather than omitting them. Keep dependent proposals sequential. If submitted content needs correction, use the platform's revision workflow or a new proposal; do not treat a submitted snapshot as editable.
- Stop after submission for human review and promotion. Never edit or promote SHARED directly. Submission, review, and preview do not publish; do not start a dependent increment while its prerequisite is awaiting promotion.
- After the human confirms promotion, reread the affected SHARED resources, verify paths, revisions, content, and validation, and use that state as the next baseline. Report implementation, technical validation, proposal, and SHARED integration as distinct states.
- Archive an owned MY WORK context only after its content is fully covered by verified SHARED and the human explicitly authorizes archival. Never delete contexts or archive partially covered work automatically. Work with no architectural impact needs no proposal.
